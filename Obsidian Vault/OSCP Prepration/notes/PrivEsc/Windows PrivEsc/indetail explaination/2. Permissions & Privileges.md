# 2. Windows Permissions & Privileges — Detailed Guide

This is one of the most important areas of **Windows privilege escalation**. The key idea is:

> **A Windows account may be able to execute something without being allowed to modify it. Privilege escalation often happens when a low-privileged user can modify an object that a higher-privileged process later trusts or executes.**

I’ll build this from the Windows security model upward, then connect each concept to pentesting/privilege-escalation methodology.

---

# 1. Windows Access Control

Windows uses an **access control model** to decide:

> **Who can access what, and what are they allowed to do?**

The major components are:

```text
User / Process
      │
      ▼
Security Token
      │
      ├── User SID
      ├── Group SIDs
      ├── Privileges
      └── Other security information
      │
      ▼
Security Descriptor
      │
      ├── Owner
      ├── DACL
      └── SACL
      │
      ▼
Access Check
      │
      ▼
Allow / Deny
```

For example:

```text
User: bob

bob tries:
C:\Program Files\App\app.exe
        │
        ▼
Windows checks the object's security descriptor
        │
        ▼
DACL contains permissions
        │
        ▼
Is bob allowed to WRITE?
        │
     YES / NO
```

### Important distinction

**Authentication**

> Who are you?

Example:

```text
Username: bob
Password: ********
```

**Authorization**

> What are you allowed to do?

Example:

```text
bob:
READ file       → YES
WRITE file      → NO
DELETE file     → NO
EXECUTE file    → YES
```

---

# 2. File & Directory Permissions

Windows permissions determine what a user or group can do with files and directories.

Common permissions include:

|Permission|Meaning|
|---|---|
|Read|Read file contents|
|Write|Modify file|
|Execute|Execute program|
|Delete|Delete object|
|Read & Execute|Read + execute|
|Modify|Read + write + execute + delete|
|Full Control|Nearly everything|
|List folder|See directory contents|

For example:

```text
C:\Tools\backup.exe
```

might have:

```text
Administrators    Full Control
SYSTEM            Full Control
Users             Read & Execute
```

A normal user can execute it but cannot modify it.

---

# 3. NTFS Permissions

**NTFS permissions** are permissions attached to objects on an NTFS filesystem.

They control access to:

```text
Files
Directories
Folders
Other filesystem objects
```

You can inspect permissions using:

```cmd
icacls C:\Users\Bob\Desktop\test.txt
```

Example:

```text
C:\Users\Bob\Desktop\test.txt

BUILTIN\Administrators:(F)
NT AUTHORITY\SYSTEM:(F)
DESKTOP\Bob:(M)
```

Meaning:

```text
Administrators → Full Control
SYSTEM         → Full Control
Bob            → Modify
```

### Common `icacls` permission abbreviations

```text
F  = Full access
M  = Modify
RX = Read and execute
R  = Read
W  = Write
```

You may also encounter inheritance flags:

```text
(I)
```

which means the permission was inherited.

---

# 4. ACLs

**ACL = Access Control List**

An ACL is essentially a collection of rules describing who can access an object and what they can do.

Example:

```text
ACL
│
├── Bob → Read
├── Alice → Modify
├── Administrators → Full Control
└── SYSTEM → Full Control
```

Each individual rule is called an:

> **ACE — Access Control Entry**

So:

```text
ACL
 ├── ACE
 ├── ACE
 ├── ACE
 └── ACE
```

For example:

```text
Bob → Read
```

is an ACE.

---

# 5. DACLs & SACLs

This distinction is extremely important.

## DACL

**DACL = Discretionary Access Control List**

It determines:

> **Who is allowed or denied access.**

Example:

```text
DACL:

Bob          → Read
Administrators → Full Control
SYSTEM       → Full Control
```

The DACL is therefore involved in the actual **authorization decision**.

---

## SACL

**SACL = System Access Control List**

It determines:

> **Which access attempts should be audited/logged.**

For example:

```text
SACL:

Audit Bob attempting DELETE
Audit Administrators attempting WRITE
```

So:

```text
DACL → Access control
SACL → Auditing
```

A useful memory trick:

> **D = Decide access**  
> **S = See/Audit access**

---

# 6. Security Descriptor

Every securable Windows object can have a **security descriptor**.

It contains important security information such as:

```text
Security Descriptor
│
├── Owner
├── DACL
└── SACL
```

Conceptually:

```text
File: C:\secret.txt

Owner:
Administrator

DACL:
Administrator → Full Control
Bob           → Read

SACL:
Audit failed access
```

You can think of the security descriptor as the object's **security metadata**.

---

# 7. Inherited Permissions

Windows supports permission inheritance.

Suppose:

```text
C:\Company
```

has:

```text
Users → Read
```

A subdirectory:

```text
C:\Company\Finance
```

may automatically inherit:

```text
Users → Read
```

And a file:

```text
C:\Company\Finance\salary.xlsx
```

may inherit it as well.

Conceptually:

```text
C:\Company
     │
     └── Finance
           │
           └── salary.xlsx
```

Permissions can flow downward.

---

## Why inheritance matters in pentesting

Suppose you find:

```text
C:\Applications
```

with:

```text
Users → Modify
```

and inside:

```text
C:\Applications\Service\service.exe
```

inherits writable permissions.

Then a low-privileged user may be able to modify the executable.

If a privileged service executes that executable:

```text
Low-privileged user
        │
        ▼
Modify service.exe
        │
        ▼
SYSTEM service executes it
        │
        ▼
SYSTEM context
```

That is a classic privilege-escalation condition.

---

# 8. Writable Files & Directories

This is one of the most important things to look for during Windows privilege escalation.

The key question is:

> **Can my current account modify something that a more privileged account/process will execute or use?**

---

## Writable executable

Suppose:

```text
C:\Program Files\VulnerableApp\app.exe
```

is executed by:

```text
SYSTEM
```

But:

```text
Users → Modify
```

on `app.exe`.

Then:

```text
Low privilege user
       │
       ▼
Can modify app.exe
       │
       ▼
SYSTEM executes app.exe
```

This creates a potential privilege-escalation path.

---

## Writable directory

Suppose:

```text
C:\Program Files\VulnerableApp\
```

is writable by normal users.

And:

```text
SYSTEM service
       ↓
runs C:\Program Files\VulnerableApp\service.exe
```

Then you need to investigate:

```text
Can service.exe be replaced?
Can dependencies be replaced?
Can DLLs be placed there?
Can configuration files be modified?
Can scripts be modified?
```

The directory's permissions can therefore be just as important as the executable's permissions.

---

# 9. Registry Permissions

The Windows Registry is another security-sensitive object hierarchy.

Important locations include:

```text
HKLM
HKCU
HKCR
HKU
HKCC
```

For privilege escalation, **HKLM** is particularly important because it contains machine-wide configuration.

Example:

```text
HKLM\Software\Microsoft\Windows\CurrentVersion\Run
```

Registry permissions determine who can:

```text
Read
Write
Create keys
Delete keys
Modify values
```

You can inspect registry permissions with tools such as:

```cmd
reg query
```

and PowerShell.

---

## Why registry permissions matter

Suppose a privileged service reads:

```text
HKLM\Software\Company\Service
```

and a low-privileged user can modify an important value.

Then the security boundary may be weakened:

```text
User
 │
 ▼
Modify registry configuration
 │
 ▼
Privileged process reads configuration
 │
 ▼
Potential privilege escalation
```

The critical concept is not simply:

> "Can I write to the registry?"

Instead ask:

> **What privileged process trusts the registry value I can modify?**

---

# 10. User Rights & Privileges

This is where Windows becomes particularly interesting.

There is a difference between:

### Permissions

Permissions generally apply to **objects**.

Examples:

```text
File
Directory
Registry key
Service
```

### Privileges

Privileges are rights assigned to a **security token**.

Examples:

```text
SeBackupPrivilege
SeRestorePrivilege
SeImpersonatePrivilege
SeDebugPrivilege
```

So:

```text
Permissions → Object access
Privileges  → Special operating-system capabilities
```

---

# 11. Windows Security Token

When a user logs in, Windows creates a **security token** associated with that user's processes.

A simplified token looks like:

```text
Security Token
│
├── User SID
│
├── Group SIDs
│
├── Privileges
│
├── Integrity Level
│
└── Other security information
```

Example:

```text
User:
CORP\Bob

Groups:
Users
Remote Desktop Users

Privileges:
SeChangeNotifyPrivilege
SeIncreaseWorkingSetPrivilege
...
```

Every process normally has an associated token.

You can inspect your identity with:

```cmd
whoami
```

and:

```cmd
whoami /groups
```

and:

```cmd
whoami /priv
```

These three commands are extremely useful in Windows privilege escalation.

---

# 12. Token Privileges

A Windows privilege has a name beginning with:

```text
Se
```

Examples:

```text
SeDebugPrivilege
SeImpersonatePrivilege
SeBackupPrivilege
SeRestorePrivilege
SeTakeOwnershipPrivilege
SeLoadDriverPrivilege
```

You can inspect privileges:

```cmd
whoami /priv
```

Example:

```text
Privilege Name                  State
=================================================
SeChangeNotifyPrivilege        Enabled
SeImpersonatePrivilege         Disabled
SeDebugPrivilege               Disabled
```

The **state** matters.

You may see:

```text
Enabled
Disabled
```

A privilege being present in the token does not necessarily mean it is currently enabled or directly usable in every context.

---

# 13. Dangerous Privileges

Some Windows privileges deserve special attention during privilege-escalation enumeration because, depending on the Windows version, token configuration, service context, and other conditions, they can provide powerful capabilities.

The major ones you should learn are:

```text
SeImpersonatePrivilege
SeAssignPrimaryTokenPrivilege
SeDebugPrivilege
SeBackupPrivilege
SeRestorePrivilege
SeTakeOwnershipPrivilege
SeLoadDriverPrivilege
SeCreateTokenPrivilege
SeTcbPrivilege
```

Do **not** memorize them as "automatic SYSTEM."

Instead:

> **A dangerous privilege is an indicator that you should investigate a specific escalation path.**

---

# 14. SeImpersonatePrivilege

This is one of the most important privileges in Windows pentesting.

It allows a process to impersonate a security token under supported circumstances.

It is commonly associated with service accounts and certain privileged service contexts.

Conceptually:

```text
Process A
   │
   │ has SeImpersonatePrivilege
   ▼
Can potentially impersonate
another security context
```

This is why:

```cmd
whoami /priv
```

is such an important command.

If you see:

```text
SeImpersonatePrivilege
```

you should recognize:

> **Investigate token impersonation-based escalation techniques.**

---

# 15. SeDebugPrivilege

`SeDebugPrivilege` allows a process to obtain powerful access to other processes, subject to Windows security protections.

Conceptually:

```text
Normal process
     │
     X
Access protected process

With SeDebugPrivilege
     │
     ▼
Much greater process access
```

This is dangerous because privileged processes may contain sensitive information or privileged security tokens.

A classic concept is:

```text
Low-privileged process
        │
        ▼
SeDebugPrivilege
        │
        ▼
Access privileged process
        │
        ▼
Potential token/process abuse
```

Modern Windows protections can complicate this significantly, so treat it as an escalation lead rather than an automatic result.

---

# 16. SeBackupPrivilege

`SeBackupPrivilege` is designed to allow authorized processes to bypass some normal file access checks when performing backups.

The important concept:

```text
Normal ACL
   │
   ▼
Access denied
```

may behave differently for a process legitimately using backup semantics.

This can provide access to files that the account couldn't normally read.

From a pentesting perspective, investigate whether sensitive data becomes accessible through backup-style access.

---

# 17. SeRestorePrivilege

`SeRestorePrivilege` is associated with restoring files and directories and can provide powerful write-related capabilities under the appropriate APIs and security model.

Conceptually:

```text
Normal write restrictions
        │
        ▼
Special restore capability
        │
        ▼
Potentially broader object modification
```

This privilege therefore deserves investigation when present.

---

# 18. SeTakeOwnershipPrivilege

This privilege allows a process to take ownership of certain securable objects.

Remember:

> **Owner ≠ full access automatically.**

But ownership gives important control over the object's security descriptor.

Conceptually:

```text
Object
 │
 ├── Owner = Administrator
 └── DACL = restrictive
```

If you can legitimately take ownership:

```text
You
 │
 ▼
Become owner
 │
 ▼
Can potentially modify security settings
 │
 ▼
Gain required access
```

This is why ownership is security-sensitive.

---

# 19. SeLoadDriverPrivilege

This allows authorized processes to load drivers.

Drivers operate at a very privileged level of the Windows architecture.

Conceptually:

```text
User mode
    │
    ▼
Kernel-mode driver
    │
    ▼
Very high privilege
```

Therefore, `SeLoadDriverPrivilege` can be extremely security-sensitive.

Modern Windows driver-signing and kernel protections make exploitation more complicated, but this privilege should immediately trigger further investigation during an authorized assessment.

---

# 20. Service Permissions

Windows services are a major privilege-escalation area.

A service has properties such as:

```text
Service name
Display name
Binary path
Start type
Service account
Service permissions
```

Example:

```text
Service: BackupService

Binary:
C:\Program Files\Backup\backup.exe

Account:
LocalSystem
```

The important question is:

> **Who can modify the service configuration or executable?**

---

# 21. Service Configuration Abuse

Suppose:

```text
Service
│
├── Runs as: SYSTEM
├── Binary: C:\Tools\backup.exe
└── Low-privileged user can modify service configuration
```

Then there may be a privilege-escalation path.

Conceptually:

```text
User
 │
 ▼
Modify service configuration
 │
 ▼
Service starts under SYSTEM
 │
 ▼
Privileged execution
```

You can inspect services with:

```cmd
sc query
```

and:

```cmd
sc qc ServiceName
```

PowerShell:

```powershell
Get-Service
```

The `sc qc` output is particularly useful because it shows configuration including the binary path and service account information.

---

# 22. Service Executable Permissions

There are actually **two different permission questions**.

### Question 1

Can I modify the service configuration?

```text
Service ACL
```

### Question 2

Can I modify the executable?

```text
NTFS ACL
```

Example:

```text
Service:
SYSTEM

Executable:
C:\App\service.exe

service.exe:
Users → Modify
```

Even if the service itself is properly protected, a writable executable could create a security problem.

---

# 23. Executable Permissions

Executables are simply files from the filesystem permission perspective.

For example:

```text
C:\Program Files\App\app.exe
```

could have:

```text
SYSTEM          Full Control
Administrators  Full Control
Users           Read & Execute
```

This is normal.

But if:

```text
Users → Modify
```

then investigate.

The dangerous combination is:

```text
Low-privileged user
        +
Writable executable
        +
Privileged execution
```

---

# 24. DLL Permissions

Don't only look at `.exe` files.

Windows programs frequently load DLLs.

Example:

```text
C:\Program Files\App\app.exe
C:\Program Files\App\helper.dll
```

If:

```text
app.exe → SYSTEM
helper.dll → Users: Modify
```

then the DLL becomes an important attack surface.

The general principle is:

```text
Privileged process
       │
       ├── EXE
       ├── DLL
       ├── configuration
       ├── scripts
       └── other dependencies
```

Any writable dependency can potentially matter.

---

# 25. Configuration File Permissions

Another frequently overlooked area:

```text
.ini
.config
.xml
.json
.yaml
.ps1
.bat
.cmd
```

Suppose:

```text
SYSTEM service
     │
     ▼
C:\App\config.ini
```

and:

```text
Users → Modify
```

You need to determine whether modifying that configuration changes:

```text
Executable path
DLL path
Command execution
Credentials
Service behavior
Plugin loading
```

Not every writable configuration file is exploitable.

The key question is:

> **Does a privileged process trust the value I can modify?**

---

# 26. Permissions vs Privileges

This distinction is critical for interviews.

### Permissions

Associated with an object:

```text
File
Folder
Registry key
Service
```

Example:

```text
C:\test.txt
Bob → Read
```

### Privileges

Associated with a security token:

```text
Bob's token
    │
    └── SeDebugPrivilege
```

So:

```text
Permissions = "What can I do to this object?"

Privileges = "What special operating-system capability does my token have?"
```

---

# 27. Owner vs Permissions

Another common interview question.

Suppose:

```text
File owner:
Administrator

DACL:
Bob → Read
```

Bob cannot necessarily modify the file merely because he knows who owns it.

Conversely, ownership is security-significant because the owner generally has the ability to modify the object's DACL.

So:

```text
Owner
  ↓
Can influence security descriptor
  ↓
Can potentially change access
```

---

# 28. Explicit vs Inherited Permissions

Consider:

```text
C:\Company
```

with:

```text
Users → Read
```

and:

```text
C:\Company\HR
```

inherits it.

Then:

```text
C:\Company\HR\employees.txt
```

may inherit the same access.

But you can also have an explicit ACE:

```text
employees.txt

Users → Read        (Inherited)
Bob   → Modify      (Explicit)
```

When investigating permissions, always determine:

> **Where did this permission come from?**

---

# 29. Permission Inheritance Diagram

Think of it like this:

```text
                 C:\Application
                       │
              Users → Read
                       │
                       ▼
                 C:\Application
                    \Service
                       │
                  inherited
                       │
                       ▼
                    service.exe
                       │
                  inherited
                       │
                       ▼
                 configuration
```

A single incorrectly configured parent directory can therefore affect many descendants.

# 30. The Most Important Privilege-Escalation Pattern

Almost everything in this topic can be reduced to:

```text
LOW PRIVILEGE
     │
     ▼
Find something writable/modifiable
     │
     ▼
Determine who uses it
     │
     ▼
Is that process/account privileged?
     │
     ▼
Can my modification influence execution?
     │
     ▼
Potential privilege escalation
```

For example:

```text
User
 │
 ├── Can modify C:\App\config.ini
 │
 ▼
SYSTEM service reads config.ini
 │
 ▼
Configuration controls executable
 │
 ▼
SYSTEM executes privileged component
```

# 31. Practical Enumeration Methodology

When you're doing a Windows privilege-escalation assessment, don't randomly inspect everything.

Use a structured process.

### Step 1 — Identify yourself

```cmd
whoami
whoami /user
whoami /groups
whoami /priv
```

Understand:

```text
Username
SID
Groups
Privileges
```

---

### Step 2 — Check filesystem permissions

```cmd
icacls C:\SomePath
```

Look for:

```text
M
W
F
```

especially on:

```text
.exe
.dll
.bat
.cmd
.ps1
.config
.ini
```

---

### Step 3 — Investigate writable directories

Look at locations such as:

```text
C:\Program Files\
C:\ProgramData\
C:\Windows\Temp\
C:\Temp\
Application directories
```

The important thing is not the directory itself.

Ask:

```text
Who can write here?
What is stored here?
Who executes those files?
When are they executed?
```

---

### Step 4 — Enumerate services

```cmd
sc query
```

Then:

```cmd
sc qc <service>
```

Look at:

```text
SERVICE_START_NAME
BINARY_PATH_NAME
START_TYPE
```

Then check the binary:

```cmd
icacls "C:\path\service.exe"
```

---

### Step 5 — Inspect registry areas

Pay attention to:

```text
HKLM\Software
HKLM\System
HKCU\Software
```

and application/service configuration.

The question remains:

> Can a low-privileged user modify something a privileged process trusts?

---

### Step 6 — Inspect privileges

```cmd
whoami /priv
```

Pay particular attention to security-sensitive privileges:

```text
SeImpersonatePrivilege
SeAssignPrimaryTokenPrivilege
SeDebugPrivilege
SeBackupPrivilege
SeRestorePrivilege
SeTakeOwnershipPrivilege
SeLoadDriverPrivilege
```

# 32. A Full Mental Model

You should eventually visualize Windows privilege escalation like this:

```text
                    WINDOWS SYSTEM
                          │
             ┌────────────┴────────────┐
             │                         │
          USER TOKEN              OBJECTS
             │                         │
       ┌─────┼─────┐           ┌───────┼────────┐
       │     │     │           │       │        │
      SID  Groups Privileges   Files  Registry Services
       │     │     │           │       │        │
       │     │     │           └───┬───┘        │
       │     │     │               │            │
       │     │     └───────────────┼────────────┘
       │     │                     │
       │     │                 ACL/DACL
       │     │                     │
       └─────┴─────────────┐       │
                           ▼       ▼
                       ACCESS CHECK
                           │
                    ┌──────┴──────┐
                    │             │
                  ALLOW          DENY
```

Then add privilege escalation:

```text
Low-privileged user
        │
        ├── Writable file
        │       │
        │       └── Privileged process uses it
        │
        ├── Writable directory
        │       │
        │       └── Privileged executable/dependency
        │
        ├── Weak service permissions
        │       │
        │       └── Service runs privileged
        │
        ├── Weak registry permissions
        │       │
        │       └── Privileged process trusts value
        │
        └── Dangerous token privilege
                │
                └── Special OS capability
```

If you're preparing for **Windows privilege escalation / OSCP-style labs**, memorize these relationships:

|Concept|Think|
|---|---|
|SID|Identity|
|Token|Security context of process/user|
|Group SID|Group membership|
|Privilege|Special OS capability|
|ACL|Collection of access rules|
|ACE|Individual access rule|
|DACL|Allow/Deny access|
|SACL|Auditing|
|Owner|Controls security descriptor in important ways|
|NTFS permissions|Filesystem access|
|Inheritance|Permissions passed from parent|
|Service ACL|Who can modify service|
|Service binary|What service executes|
|Registry ACL|Who can modify registry objects|
|Writable EXE|Potential execution hijacking|
|Writable DLL|Potential dependency hijacking|
|Writable config|Potential privileged behavior modification|

And these commands should become automatic:

```cmd
whoami
whoami /user
whoami /groups
whoami /priv

icacls <file>
icacls <directory>

sc query
sc qc <service>

reg query <key>
```

# 34. The Core Questions to Ask

For **every permission/privilege finding**, ask these five questions:

### 1. Who am I?

```text
User?
SID?
Groups?
Integrity level?
```

### 2. What can I modify?

```text
File?
Directory?
Registry?
Service?
Configuration?
Token privilege?
```

### 3. Who normally uses it?

```text
My account?
Another user?
Administrator?
SYSTEM?
A service account?
```

### 4. How is it used?

```text
Executed?
Loaded?
Read?
Written?
Loaded as DLL?
Used as configuration?
Started by service?
```

### 5. What security boundary does it cross?

```text
USER
  ↓
SERVICE ACCOUNT
  ↓
ADMINISTRATOR
  ↓
SYSTEM
```

That final question is what turns simple **permission enumeration** into actual **privilege-escalation analysis**.
