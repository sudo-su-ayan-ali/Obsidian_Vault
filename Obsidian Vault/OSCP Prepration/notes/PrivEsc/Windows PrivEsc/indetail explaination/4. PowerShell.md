PowerShell is one of the most important tools for **Windows privilege escalation** because it gives you a programmatic interface to users, groups, processes, services, ACLs, registry, scheduled tasks, networking, environment variables, and Windows security mechanisms.

For an authorized lab such as **TryHackMe, Hack The Box, VulnHub, or your own Windows VM**, the key skill is not memorizing commands. It is learning to answer:

> **“What is different or misconfigured on this Windows system that allows my current user to gain additional privileges?”**

Below is a structured deep dive.

---

# 4. PowerShell for Windows Privilege Escalation

## 0. The PowerShell PrivEsc Mental Model

Think of PowerShell enumeration as a pipeline:

```text
Current Identity
      ↓
Users & Groups
      ↓
Processes
      ↓
Services
      ↓
Files / Directories
      ↓
ACLs / Permissions
      ↓
Registry
      ↓
Scheduled Tasks
      ↓
Network
      ↓
Environment
      ↓
Security Controls
      ↓
Misconfiguration / Vulnerability
      ↓
Privilege Escalation
```

For example:

```text
Low-privileged user
        ↓
Finds service running as SYSTEM
        ↓
Service executable is writable
        ↓
Current user can modify executable
        ↓
SYSTEM executes modified program
        ↓
Privilege boundary is crossed
```

The important part is that **enumeration comes before exploitation**.

# 1. PowerShell Fundamentals

## 1.1 What is PowerShell?

PowerShell is Microsoft's command-line shell and scripting environment.

Unlike traditional `cmd.exe`, PowerShell works heavily with **objects**.

For example:

```powershell
Get-Process
```

doesn't simply return text.

It returns `System.Diagnostics.Process` objects.

You can pipe those objects into another command:

```powershell
Get-Process | Where-Object {$_.CPU -gt 100}
```

Conceptually:

```text
Get-Process
     ↓
Process objects
     ↓
Where-Object
     ↓
Filter
```

This is extremely useful for enumeration.

---

Examples:

# 1.4 Object Properties

Suppose:

```powershell

```

returns processes.

You can inspect their properties:

```powershell

```

`Get-Member` is extremely important.

It tells you what properties and methods an object has.

For example:

```powershell
Get-Process | Select-Object Name,Id,Path
```

You are selecting specific object properties.

# 1.5 Pipeline

PowerShell's pipeline is one of its most important features:

```powershell
Get-Process | Where-Object {$_.Name -eq "explorer"}
```

Another example:

```powershell
Get-Service |
    Where-Object {$_.Status -eq "Running"}
```

You can chain operations:

```powershell
Get-Service |
    Where-Object {$_.Status -eq "Running"} |
    Select-Object Name,DisplayName,StartName
```


## 4.1 Why Processes Matter

You want to understand:

```text
Which processes are running?
Who owns them?
What executable launched them?
Where is that executable?
What arguments were supplied?
Is the executable writable?
Is sensitive information exposed?
```

For example:

```text

    ↓
```

## 5.1 Service Configuration

Use CIM:

```powershell

```

Important properties:

```powershell

    Select-Object Name,
                     DisplayName,
```


---

## 5.2 Important Service Scenario

Imagine:

```text
Service: BackupService
Account: NT AUTHORITY\SYSTEM
Path:
C:\Program Files\Backup\backup.exe
```

Then you discover:

```text
Current user:
Write permission on backup.exe
```

The interesting relationship is:

```text
USER
 ↓
can modify executable
 ↓
SYSTEM service executes executable
 ↓
SYSTEM context
```

The vulnerability isn't simply:

> "A service exists."

It is the combination of:

```text
High-privilege service
+
modifiable executable/configuration
+
ability to trigger execution
```

# 7. Permission Enumeration

This is arguably more important than simply finding files.

Finding:

```text
C:\Scripts\backup.ps1
```

doesn't automatically mean anything.

You need to ask:

> **Can my current identity modify it?**

---

# 7.1 NTFS ACLs

PowerShell:

```powershell
Get-Acl C:\Scripts\backup.ps1
```

Example:

```powershell
(Get-Acl C:\Scripts\backup.ps1).Access
```

This exposes ACEs such as:

```text
IdentityReference
FileSystemRights
AccessControlType
IsInherited
```

---

# 7.2 Understanding Rights

Interesting rights include:

```text
FullControl
Modify
Write
WriteData
AppendData
Delete
WriteAttributes
WritePermissions
ReadAndExecute
```

A simplified interpretation:

```text
Read
    ↓
Can inspect

Write
    ↓
Can modify content

Modify
    ↓
Can modify/delete in many situations

FullControl
    ↓
Broad control including permission changes
```

---

# 7.3 Inheritance

Windows ACLs often use inheritance.

For example:

```text
C:\Program Files\Company\
        ↓
       ACL
        ↓
C:\Program Files\Company\app.exe
```

The file may inherit permissions from its parent directory.

Check:

```powershell
(Get-Acl "C:\Program Files\Company\app.exe").Access |
    Format-Table
```

Pay attention to:

```text
IsInherited
```

# 8.2 Registry Permissions

This is the important PrivEsc concept.

```powershell
Get-Acl "HKLM:\SOFTWARE\SomeApplication"
```

Again:

```text
Can current user write?
Can current user modify?
Can current user create subkeys?

```

A writable security-sensitive registry location can sometimes create a privilege-escalation path.

---

# 8.3 Run Keys

Windows has registry locations associated with startup execution.

For example:

```text
HKCU\Software\Microsoft\Windows\CurrentVersion\Run
```

and:

```text
HKLM\Software\Microsoft\Windows\CurrentVersion\Run
```

Enumeration:

```powershell
Get-ItemProperty `
"HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
```

These are useful during broader persistence and privilege-escalation enumeration, but context matters: a normal user-level Run key generally gives user-context execution, not automatic SYSTEM privileges.

# 11. Environment Variable Enumeration

Environment variables are frequently overlooked.

List them:

```powershell

```

```powershell

```

Individual variable:


---

## 11.1 PATH

`PATH` is particularly important.

```powershell
$env:PATH -split ';'
```

You might see:

```text
C:\Windows\System32
C:\Windows
C:\Program Files\Something
C:\Users\user\AppData\Local\Programs
```

The security question is:

> **Is an executable search path directory writable by a lower-privileged user while a privileged process relies on it?**

This leads into concepts such as:

```text
PATH hijacking
DLL search-order issues
Unquoted service paths
Executable search-order behavior
```

These require careful validation rather than assuming every writable PATH directory is exploitable.


---

# 13.1 Important Misconception

Execution Policy is **not a complete security boundary**.

For example:

```text
Restricted
```

does not mean:

> "PowerShell cannot execute arbitrary code under any circumstances."

Execution Policy primarily governs script execution behavior and can be influenced by configuration scope and other mechanisms.

Therefore, don't treat:

```powershell
Get-ExecutionPolicy
```

as equivalent to:

```text
Is PowerShell secure?
```

It isn't.

# 15. PowerShell-Based Privilege Escalation

PowerShell itself isn't a vulnerability.

Typical workflow:

```text

   ↓

   ↓
Identify anomaly
   ↓

   ↓

   ↓

```

# 16. PowerUp

**PowerUp** is a PowerShell-based Windows privilege-escalation auditing framework associated with the PowerSploit project.

Its purpose is to identify common Windows privilege-escalation misconfigurations.

Conceptually, it checks areas such as:

```text
Services
Service permissions
Unquoted service paths
Registry configuration
Scheduled tasks
DLL search paths
AlwaysInstallElevated
Credential-related configuration
Writable files/directories
```

The important concept isn't:

> "Run PowerUp and get SYSTEM."

Instead:

> **PowerUp automates a large amount of the enumeration you should understand manually.**

---

## 16.1 Why Learn Manual Enumeration First?

Suppose PowerUp reports:

```text
Service X is potentially vulnerable.
```

You need to understand:

```text
Why?
 ↓
Which account runs it?
 ↓
What executable does it launch?
 ↓
Who can modify it?
 ↓
What ACL permits modification?
 ↓
Can execution actually be triggered?
```

Without that understanding, automated output becomes a list of unexplained findings.

```text
Potential vulnerabilities
```


# 17.1 WinPEAS Output

For example:

```text

[+] Scheduled Tasks

[+] Registry
```

# 21. The Most Important PrivEsc Relationships

When you enumerate a Windows machine, don't just collect isolated facts.

Look for **relationships**.

### Relationship 1 — User → Group

```text
Current user
      ↓
Member of privileged group
```

---

### Relationship 2 — User → File

```text
Current user
      ↓
Can modify privileged executable
```

---

### Relationship 3 — User → Service

```text
Current user
      ↓
Can modify service configuration
      ↓
Service runs as SYSTEM
```

---

### Relationship 4 — User → Scheduled Task

```text
Current user
      ↓
Can modify task executable/script
      ↓
Task runs as SYSTEM
```

---

### Relationship 5 — User → Registry

```text
Current user
      ↓
Can modify security-sensitive registry configuration
      ↓
Privileged component consumes configuration
```

---

### Relationship 6 — User → Process

```text
Privileged process
      ↓
Weak access control
      ↓
Current user can interact with it
```

# 24. The Core Windows PrivEsc Chain

Eventually, you should be able to look at a machine and construct something like:

```text
Current user
    │
    ├── Groups
    │
    ├── Privileges
    │
    ├── Processes
    │
    ├── Services
    │       │
    │       └── SYSTEM service
    │               │
    │               └── Writable executable
    │
    ├── Scheduled Tasks
    │       │
    │       └── SYSTEM task
    │               │
    │               └── Writable script
    │
    ├── Registry
    │       │
    │       └── Weak ACL
    │
    └── Files
            │
            └── Sensitive/writable configuration
```

Then you validate each potential path.

The most important skill is recognizing:

> **Low-privileged principal → weak access control → privileged execution context → controllable execution path.**

That pattern appears repeatedly in Windows privilege escalation.
